The game

The game at a glance

Source: src/app/GameApp.tsx:17

Idle Realm (code name idlarz) is an idle/incremental map game for signed-in players. Everything here describes only what the code does now, with the symbol each number comes from.

The loop of the game

  1. You start with a castle and the four tiles beside it on an unbounded map, 125 gold and 1,000 gems. Gold, other resources and XP trickle in (BASE_GENERATION_RATES).
  2. Gold (plus wood, stone, coal, food and hide from tile 15 up) buys adjacent tiles (tilePrice); each becomes a randomly rolled biome (rollBiome) and adds income. Buildings stand on tiles and add output. Same-biome neighbours add 25% each.
  3. The castle is a timed upgrade (level 1-10) that adds a big modifier to every resource, a range bonus on nearby tiles, and a ward from level 7 that keeps monsters out (CASTLE_UPGRADE).
  4. The farm turns food into animals that make meat and small amounts of eggs, milk and hide (ANIMALS). The merchant buys resources, sells gear and potions, and sells permanent upgrades for gold (MERCHANT_UPGRADES).
  5. Clicks on the map and chests add active gold (clickGold, CHEST). Every level gives attribute points (Strength, Dexterity, Intelligence, Vitality, Charisma) that add income, combat strength, Luck and a tile discount (CHARACTER_STAT_CONFIG).
  6. Monsters appear on owned land (advanceBank). You click one and the server runs the fight (runCombat); wins pay gold, XP, hide and gear (killIncome, generateLoot). Gear comes only from fights, chests and the merchant's shelf.
  7. Rebirth (castle 6 and 400+ tiles) restarts the map for Embers: a permanent income bonus and a shop (REBIRTH). Level, XP, Embers and shop levels stay; map, gear and merchant upgrades (except Pack Rat) do not.

Time scale. Timers that set the pace: castle upgrades 30 min to 3.5 days per level; a monster every 15 minutes and a boss every 3 hours (COMBAT.spawn); a chest every 10 minutes (CHEST.intervalSec); away time paid up to 8 hours at 50% (LIMITS). Measured pacing from the bot simulation is in docs/generated/sim-milestones.md; targets are on the Pacing page.

Where the numbers live. Config is data (src/config/*, src/catalog/*), maths is pure functions next to it (src/utils/game/*, src/lib/*), the server engine is src/lib/offline/* + src/app/api/*. This reference points at all of them; the generated code-map.md lists every file with its first comment.

Not in the game yet: hills, coast and lake monsters; jungle, fields, orchard, blight and battlefield biomes (dev-only entries); the Producer/Extractor/Idol building rework; quests; gambling; achievements, glossary and mastery; real class bonuses; paragon levels; rankings and the preview map; landing page and /play route; the guided tutorial rework; gem sinks. Details: docs/plan/ROADMAP.md. Crafting (queue, recipes) exists but is still a first draft: docs/plan/crafting-v0.md.

Conventions

Source: src/app/GameApp.tsx:2

Conventions that hold for the whole code base.

  • Rates are per second and before modifiers unless stated; modifiers are fractions (0.25 = +25 %).
  • Anything that moves resources is validated in the store action and covered in tests/economy/economy.test.ts; anything that is saved is validated in src/lib/sanitizeSave.ts (sanitizeSave); anything that decides a reward or a fight lives on the server side (src/lib/offline/).
  • Documentation lives in the JSDoc next to the code (this reference is generated from it, see the README of this folder). When the code changes, change its block in the same edit; a pre-commit hook regenerates docs/reference. docs/plan/ holds the plans for what is not built; a built draft leaves plan/ and is described here, in the JSDoc.
  • Config is data, maths is pure functions. Tutorial, stat tooltips and cost lists are generated from config constants so they cannot drift from the rules.
  • Reports measured from the game (docs/generated/*, written by npm run docs:gen) are never edited by hand; prefer a link to them over copying numbers into prose, and prefer @table over numbers typed into JSDoc.

Basics: tick, caps, start

Source: src/config/economy.ts:22

Game constants the economy runs on: the tick, the caps, the start.

What the game does is read from the code; every number below is computed from the config. Where a doc and the code disagree, the code wins.

  • The browser ticks every 100 ms and one tick never advances the game by more than 300 s (MAX_CATCHUP_SEC), so a throttled tab catches up in 5-minute steps and a changed system clock can neither skip nor reverse time. Away time is not computed here but claimed from the server (see computeOfflineGrant).
  • Every stockpile, XP included, stops at RESOURCE_CAP; a save above it is treated as tampered.
  • Gems and Embers are not part of the Resources record: gems are the server's balance (see STARTING_GEMS), Embers live in the prestige state (see REBIRTH).

Income

calculateResourceBreakdown function

Source: src/utils/game/income.ts:133

Income per second of every resource, split into its sources and modifiers (the one place the income formula lives).

The one function that builds the income. Every number the UI shows as "per second" (header, tooltips, the tick) comes from here.

Everything inside the first bracket is added, the three multipliers after it are multiplied. The meat and hide of the farm are multiplied by the merchant's Skinner before they enter base. The castle tile itself gets no yield scale and no neighbour bonus.

  • plainsMod: +5% meat per owned Plains tile (CHARACTER_STAT_CONFIG.plainsMeatModifier).
  • statMod: +2.5% per attribute point on the resources each attribute feeds, and +0.2% / +0.25% XP per Intelligence / Charisma point, see calculateStatResourceModifiers.
  • emberMult: see emberIncomeBonus.
  • foreman: the merchant upgrade, +1% per level on every resource but XP. gearIncome: the set bonus Income %, on every resource but XP (src/lib/gearEconomy.ts).

Formula

base[r]  = BASE_GENERATION_RATES[r]
         + farm output (meat, eggs, milk, hide; the farm has no other source of those four)
         + sum over owned tiles of (biome output[r] + building output[r]) x BIOME_YIELD.scale x (1 + 0.25 x same-biome 4-neighbours)
         + sum over tiles inside the castle range of the same tile output x castleAreaBonus(castle level)
         + 0.5 x (castle level - 1)                      (xp only)
modifier[r] = (1 + castleModifier + plainsMod[r] + statMod[r]) x emberMult x foreman x gearIncome - 1
total[r] = base[r] x (1 + modifier[r])

See also: calculateTileOutput, castleModifier, castleAreaBonus, calculateFarmOutput

tilePrice function

Source: src/config/economy.ts:106

Gold price of the next tile when ownedTiles are owned, before discounts: the three exponential stages of SCALING_CONFIG up to TILE_PRICE.tailFrom, then the polynomial tail, never above TILE_PRICE.ceiling. Always finite.

Buying a tile: a tile can be bought when it touches an owned tile on one of its four sides and the whole bundle is paid.

The count that feeds every price is the economy count (economyTiles). A new game owns the castle and the four tiles N/E/S/W, so the first purchase is "tile 1". The constants are BASE_TILE_COST 55, the three stages in SCALING_CONFIG (1.13 to 15 tiles, 1.07 to 100, 1.007 to TILE_PRICE.tailFrom 300) and TILE_PRICE.tailExponent 3.5. The extra resources a purchase asks for are in TILE_RESOURCE_COST; discounts in calculateTileCost.

Formula

m        = min(n, 300)
price(n) = floor(min(55 x 1.13^min(m,15) x 1.07^max(min(m,100)-15, 0) x 1.007^max(m-100, 0) x (n/300)^3.5 [only if n > 300], ceiling))
ceiling  = RESOURCE_CAP / 100

Biomes

rollBiome function

Source: src/utils/biomeRules.ts:126

The biome of a random purchase on (x, y): first a chance to continue an adjoining area (stronger with every extra same-biome neighbour), otherwise a weighted roll among everything the rules allow. Water still pulls water and shore (BIOME_SPAWN). Always returns an allowed biome (plains is never blocked).

Which biome a purchase becomes is rolled when you buy; there is no picker. Rules and numbers are BIOME_RULES in src/config/biomeRules.ts and BIOME_SPAWN in src/config/biomes.ts.

  • Plains, forest, hills and lake from the start; swamp after 6 purchases, tundra after 10; coast only beside a lake or coast.
  • Never adjacent (8 neighbours): tundra-swamp, tundra-coast, hills-coast. Plains is neutral.
  • Clustering: a base chance to copy a neighbouring biome (forest 60, hills 55, lake 50, swamp 55, tundra 65, plains 45, coast 40) plus 10 per extra same-biome 4-neighbour, capped at 90%; a lone tile joins a neighbour with buddyPct 100.
  • Otherwise a weighted roll: every biome 1, coast 0.6, lake and coast likelier beside water.
  • Jungle, fields, orchard, blight and battlefield exist in BIOMES as dev-only entries; no rule gives them to players.
  • The start ring (the four free tiles) is plains and forest only, at least two plains (generateStartRing).

armorReduction function

Source: src/lib/combat.ts:207

The share (0-0.75) of a hit that armor takes away: armor / (armor + K) up to 50 %, then every further point counts half as much, so no amount of armor makes anything unkillable (the asymptote is 75 %).

Armor reduction: r = armor / (armor + 40); up to 50% the reduction is r, above that every extra point counts half, so the ceiling is 75% (COMBAT.armorK, armorSoftCap, armorSoftSlope). A monster hit does max(1, round(attack x (1 - reduction))) (mitigate). The same curve is used for the player's armor and for monster armor.

Formula

r         = armor / (armor + 40)
reduction = r                         if r <= 0.5
          = 0.5 + (r - 0.5) x 0.5     above that       (ceiling 0.75)

A fight

runCombat function

Source: src/lib/offline/fight.ts:61

Brings the player's combat up to env.nowSec, then applies what the player asked for (switches, hotkeys) and starts the next fight when auto-battle allows. Returns the new ledger. All events are in ledger.combat.log.

A fight. runCombat fast-forwards the player's combat to the server clock in 0.1 s ticks (COMBAT.tickSec) on every request; at most 120 s of fighting per request (maxCatchUpSec), then it reports behind.

Per tick (fightStep):

  1. HP and mana regenerate, cooldowns run, the boss clock runs, auto-use may act.
  2. The player swings every 1 / attacks per second. A swing rolls crit, then super crit (swing; two random numbers at most). Damage to the monster is max(1, round1(hit x (1 - armorReduction(monster armor)))). Life leech heals damage x leech%.
  3. If the monster is dead the kill is paid (payKill) and the fight closes.
  4. The monster swings every 1 / attackSpeed (a stunned monster's timer does not advance). Dodge is rolled first; a monster crit uses its critChance and critMult (1.5).
  5. At 0 HP the fight ends defeated: HP is set to 30% of max (knockoutHpFraction). If the boss clock reaches 0, or a fight lasts 180 s (maxFightSec), it ends timeout. Neither costs anything; the monster stays. retreat (switching auto-battle off) also keeps it.

The random stream is sealed per swing (rngFor), so a fight is a pure function of profile, ticket and secret. tests/combat/goldenFight.test.ts pins the engine to recorded fights; tests/combat/fightBalance.test.ts pins the plains boss tuning; npm run fight-sim and npm run monster-ladder print which gear beats which monster (docs/generated/).

See also: fightStep, estimateWin, restThrough

Starting a fight.

  • Click on a monster (CombatCommand fight): fights it at once whatever the HP, the retry time, and with auto-battle on or off. Refused with a fight open (it queues instead), at 0 HP, or while the server is behind.
  • Auto-battle (switch, default off, locked until the first rebirth: COMBAT.auto.minRebirths = 1, autoBattleUnlocked): when HP is at least 80% of max (resumeHpPct) the server picks the next placed monster: weakest level first (engageOrder), normal monsters before a boss, skipping any monster whose win chance is below 0.5 (minWinChance) or whose retry time has not passed. A monster that beat the player (or timed out) waits 300 s (a boss 600 s) (retryCooldownSec, bossRetryCooldownSec). See also engage.
  • Dismiss removes a monster for good (no loot), not allowed for the monster being fought (dismissTicket).

Pipeline

generateLoot function

Source: src/lib/loot/generate.ts:317

Everything one source gives. data and rng are injectable so tests and the simulator are reproducible.

The one loot pipeline. Every source (monster, boss, chest, the merchant's shelf) goes through it:

source -> loot profile -> roll count -> source level -> item level -> eligible items -> rarity -> item -> instance (+ bonus tables)

Quantity, rarity, level and eligibility are separate steps; nothing in the generator names a rarity, an item or a monster. Data is src/catalog/lootConfig.ts (sources, profiles, pools), src/catalog/rarity.ts, src/catalog/affixes.ts and the item catalog; the code is pure, with an injectable rng, so tests and npm run loot-sim are reproducible.

  1. A source (LOOT_SOURCES) names a profile. A monster passes its own level; a chest and the shelf get theirs from the castle level (resolveSourceLevel); never from the player's level.
  2. The profile's rolls decide how many equipment rolls succeed: a random count in min..max, the first guaranteed always, the rest at chancePerRoll + chancePerLevel x (level - 1), times the Luck drop-chance multiplier (dropChanceMultiplier). A lucky monster adds extraGearRolls.
  3. Each success rolls an item level around the source level (offset +/- variance, clamped to the profile and to maxItemLevel, rollItemLevel).
  4. The eligible items are the profile's pool members whose item level window contains that level (and whose grade is at most maxGrade).
  5. The rarity is rolled from the profile's relative rarityWeights among the rarities that have an eligible base at that level and pass rarityLevelGate; Luck multiplies the weights of rare and better (rarityLuckMultiplier), so the other rarities lose share, not weight.
  6. The item is a weighted pick among the candidates of that rarity; an instance gets a quality roll (0-100) and, from the rarity's affix count, affixes picked without replacement, one per group.
  7. Bonus tables add reward channels on top: a targeted pool (named items), potions, a boss's own pool. placement says how a table combines with the general rolls: extra adds (default), fallback only runs when no equipment has dropped, replace cancels the gear when it triggers (a chest's legendary weapon). A table may carry pity: each miss adds perMiss to its chance (up to maxBonus), a drop resets it.

Drops reach the bag through receiveDrops: the auto-sell filter (isAutoSold) sells what it matches, the rest goes into the bag, and what does not fit turns into gold.

See also: LOOT_SOURCES, LOOT_PROFILES, receiveDrops, validateLootData

levelScale function

Source: src/catalog/stats.ts:195

Power multiplier of an item level (1 at level 1).

Item power grows linearly with item level: each level adds 7% of the level-1 power (1 at level 1, 1.63 at 10, 7.9 at 100). Gear is authored at its own minItemLevel; an instance of level L has baseStats x levelScale(L) / levelScale(minItemLevel), then the quality roll (+/-8%). Affix values use the same curve. Formula

levelScale(L) = 1 + 0.07 x (L - 1)         L clamped to 1..100 (MAX_ITEM_LEVEL)
stats(instance) = baseStats x levelScale(L) / levelScale(minItemLevel) x (1 + (quality - 50) / 50 x 0.08)

LEVELING const

Source: src/config/character.ts:55

Character level 1-100 (maxLevel). XP is lifetime and carries over a rebirth, so the curve is paced over rebirths, not days.

The curve is written as anchors, the total XP needed to reach a level: 10 -> 1.4e5, 30 -> 1.0e8, 80 -> 3.0e9, 90 -> 6.5e9, 100 -> 1.85e10. The first step (level 1 to 2) is 5,000 XP (firstStepXp). Threat model

The server's rule and the threat model

Source: src/lib/cloudSave/pipeline.ts:1

What the browser keeps, what the server keeps, and what the server decides.

The rule of the game. The game needs an account (there is no guest mode). The browser holds the game state and runs the economy (income, purchases, the map, the farm, the merchant's prices, stat allocation, rebirth bookkeeping). The server owns what is worth cheating for: when chests and monsters appear and where they stand, every kill and chest reward, every fight, the gem balance, the bag and worn gear, away-time pay, the XP ceiling and the Ember bound. The server judges the browser's save by plausibility, not by replaying actions.

judgeRebase function

Source: src/lib/cloudRecovery.ts:31

Whether a refused upload (409, "the account has a newer save") may be resolved without asking the player, and how. Decided from numbers both sides hold, never from anything the server could be asked to trust. The server's own revision check stays as it was: the browser only re-bases on the revision it is told about.

  • ahead: this browser's game is the same game and at least as far along (cloud revision above the link's; cloud not ahead in play time, level or tiles; same rebirth). Uploading over it loses nothing.
  • overwrite: the account's save continued from this browser's link (revision above the link's) but holds more than this browser's game, and nobody has saved it for QUIET_MS: the other session is gone, so this browser's game replaces it (owner decision). The server pins the replaced save in the history first (losesProgress), and the player is told. While the other session is still saving, the browser waits (wait), so two live sessions never trade overwrites.
  • never: the revision is not above the link's (a New Game elsewhere starts the revisions again): another game, the player chooses in the hub.

Formula

continued = cloud.rev > link.rev; ahead = continued && cloud.playSeconds <= local.playSeconds && cloud.level <= local.level && cloud.tilesOwned <= local.tilesOwned && cloud.rebirths == local.rebirths; overwrite = continued && !ahead && now - cloud.serverSavedAt >= QUIET_MS

Accepting a save

acceptSave function

Source: src/lib/cloudSave/pipeline.ts:201

Accepts a save from a client that says it was based on revision baseRev (0 = this account has no save yet).

  • the text must decode (checksum, schema, sanitizeSave), otherwise invalid
  • a stale baseRev is a conflict: the player picks a side in the hub, nothing is overwritten silently
  • the stored copy is rebuilt from the sanitized state, and rates and headline numbers are computed here
  • the spending check and the transition from the previous save are verified; each flag has a decision in FLAG_POLICY (flag, clamp or reject; reject only while ENFORCEMENT.enabled, shadow mode otherwise)
  • the map is only written when it changed; every ~30 min (by the clock) and when a new flag appears a full copy goes to the history

Accepting a save (POST /api/save):

  1. The user id comes from the session cookie only; the body is capped at 600,000 bytes (SAVE_BODY_MAX); at most one accepted save per 10 s per account (MIN_SAVE_INTERVAL_MS).
  2. The text must decode (checksum, schema, sanitizeSave). The stored copy is rebuilt from the sanitized state; rates and headline numbers are computed on the server (summarize in cloudSave/summary.ts).
  3. baseRev must equal the stored rev (compare-and-swap) or the answer is conflict.
  4. The server's inventory (bag, gear, pity, auto-sell) is stamped over the upload before anything is derived (a rebirth wipes it once, a New Game takes the new game's).
  5. The checks of verifyTransition run, each producing a flag with a policy in FLAG_POLICY.

History: a full copy goes to save_history every 30 minutes of the clock and when a new flag appears; 6 newest + 3 pinned per player (HISTORY_EVERY_MS, HISTORY_KEEP, PINNED_KEEP). Test accounts: a save through a non-production server marks the account test_account (sticky); its flags never count and it is never ranked (isNonProduction). Ranking eligibility (trusted): the first save was a young game (<= 900 s of play) and no poison flag was ever raised (POISON_FLAGS).

XP_MODEL const

Source: src/lib/cloudSave/xpModel.ts:21

The server's model of how much XP a character can have. XP is lifetime progress (it carries over a rebirth), and most of it comes from buying tiles, which the browser does by itself. The server therefore adds up what two consecutive saves can explain, from numbers it derives itself: the XP of the tiles bought in between (the same calculateXpGain the game uses), the passive XP of the play time (rates x the time that really passed), and what the server itself paid (kills, chests, absences: the ledger's grants). That sum is kept from save to save as derived.xpBase; a save that holds more than the base plus a one-off headroom is clamped to it (and flagged).

Generous on purpose: an honest player is never clamped (the numbers include a margin for gifts and rounding), while XP out of thin air is bounded by what the player has really bought and played.

In short: allowed = tile XP of the bought tiles x 1.02 + passive XP x 1.25 + server grants, plus a headroom of 900 s of income or 2,000. The first save may hold 3x that. The browser takes the lower XP the server returns.

EMBER_MODEL const

Source: src/lib/cloudSave/emberModel.ts:29

The server's model of how many Embers (and rebirths) an account can hold. Embers multiply the income of every resource but XP (1 + 0.1 x earned^0.6), and the server derives offline pay, kill rewards and chest gold from the stored save, so a save that claims Embers no rebirth paid would pay out for real. Until the server runs the rebirth itself (/api/rebirth, IDL-102) the browser still does, so the server bounds what two consecutive saves can explain, from numbers it already holds (IDL-166):

  • Embers only rise together with the rebirth count: a save at the same rebirth count cannot hold more than the last one did (buying shop levels lowers the unspent points, never the Embers ever earned).
  • A rebirth is believable when the previous save was at castle level 6 or more (a running upgrade counts) with the territory the next rebirth needs, give or take the tiles bought since; at most one rebirth fits between two saves.
  • The gain is at most what the previous save's castle and territory pay, with the Ancestral Tithe at its maximum (the merchant upgrades bought without gold are put back by the trusted economy, IDL-168, but a Tithe bought since the last upload is not known here).
  • A first save (nothing to compare with) holds a whole history: its rebirths are bounded by the play time and its Embers by the best rebirth the game can pay.

In short: Embers only rise with the rebirth count; one rebirth fits between two saves and it must be believable from the previous castle and land; a first save is bounded by 4 hours of play per rebirth and a 1,000-tile best case. requireServerRebirth is off.

Away time

computeOfflineGrant function

Source: src/lib/offline/grant.ts:70

The grant for an absence of gapSec, or null when it is shorter than the minimum (nothing to show). Income is piecewise: if the castle upgrade finishes while away, the rest of the time earns at the higher rates. Amounts are rounded down.

Away time (/api/offline).

  • Gap = server clock now minus the later of the ledger anchor and the last accepted save. Gaps shorter than 300 s (offlineMinGapSec) pay nothing.
  • elapsed = min(gap, cap) with cap = 8 h + Night Watch + set hours (hard 72 h).
  • Paid = rates x elapsed x efficiency, efficiency = 50% + Steward + set points (hard 100%); XP also times (1 + XP gain %); floored. If the castle upgrade finishes during elapsed, the rest is paid at the higher rates.
  • Castle timers and monster growth run at full speed for the whole elapsed; chests and monsters arrive at the efficiency rate.
  • Online calls are refused with claim_first when more than UNCLAIMED_SEC passed since the player was last seen; a gap over 900 s also rests the hero (restThrough). The client heals HP/mana fully for a gap of 600 s or more (FULL_HEAL_AFTER_SEC in src/lib/offline/apply.ts).
  • Write-skipping: a poll that moved only the clock does not write the ledger unless the anchor fell 120 s behind (ANCHOR_REFRESH_MS).

Formula

elapsed = min(gap, 8 h + Night Watch hours + set hours)           (hard cap 72 h)
paid[r] = floor(rate[r] x elapsed x efficiency)                    efficiency = min(1, 0.5 + 0.05 x Steward level + set points)

Browser state

BASELINE_EPOCH const

Source: src/lib/epochGuard.ts:26

The browser's half of the data epoch. A server reset (the New chapter release flips the server's GAME_EPOCH, IDL-76) leaves this browser holding state that belongs to the old game: the cloud link (a revision the account no longer has: 409 loops, or no_save 404s), upload attempts, the combat log cursor, a pending offline claim, the manual save cooldown, the conflict counters, the tab's "entered" flag and the local save itself.

The browser remembers the epoch it last saw (localStorage idlarz.epoch). When /api/auth/me reports a higher one (epochVerdict says wipe), the local save is put aside (archiveForNewGame) and reset, every key above is cleared (wipeStaleBrowser), the new epoch is recorded last (a failed wipe is simply tried again on the next load) and the page reloads into the normal start check, which finds an account with no save and starts a new game with a fresh link. No epoch in the reply (the server does not send one yet) means the guard does nothing. A browser with no stored epoch counts as BASELINE_EPOCH, the value the server has today, so every browser that predates the guard is wiped on the flip and a brand new one is not.

What this cannot do: a tab that is already open when the epoch flips never asks /api/auth/me again. That tab is stopped by the server (a save from an old epoch has to be refused there), not by this guard. See docs/plan/reset-proof-browsers.md.

Architecture

Stack, state, the tick loop, the map, rendering and the art pipeline.

The loop

The tick loop and persistence

Source: src/app/GameApp.tsx:111

The tick loop. GameApp runs setInterval(..., 100 ms) only in the owning tab (one tab owns the game through a Web Lock, useSingleTab) and only after the save is loaded and the offline claim is done. Each interval computes deltaTime = performance.now() - last (monotonic) and calls store.tick(deltaTime); tick clamps the delta to 0 ... MAX_CATCHUP_SEC (300 s), so a throttled background tab catches up in 5-minute steps but a changed system clock can neither skip nor reverse time. Offline progress is not computed here: a player's absence is claimed from the server before the loop starts (computeOfflineGrant).

tick order: accumulate resources -> XP (with xpGainMultiplier) -> castle upgrade timer (finishing recomputes the rates) -> age the monsters on the map (advanceMonsters; the server places them) -> HP / mana regeneration and cooldowns (in a fight the server's HP is left alone) -> merchant stock rotation -> level / stat points -> one set(). The tick does not spawn chests or monsters and does not run fights.

useSpawnSync polls /api/spawn (it waits until the next ticket is due, 20 to 600 s; an open fight is polled once, when the plan it was sent says it ends (a fight the server could not plan: every 2 s, a minimized one every 8 s), and the boss timer and the bars run on the browser between answers; a fight action also triggers an immediate sync): the server answers with the chests and monsters that have appeared (applyServerTickets -> reconcileMap places them on the map), the gem balance and the combat view (HP, mana, cooldowns, the open fight). A click on a monster calls startFight, which asks /api/fight to open the fight; from then on the server swings both ways in fixed ticks, with or without the browser.

Clicks. useClickIncome (called by GameHeader) registers one window click listener. A click counts only if it is trusted and lands inside [data-click-area] (the map). It calls clickForGold, which asks the limiter (createClickLimiter) with the event's timeStamp as id, so one physical click costs one token. Nothing hits a monster by clicking: a click on a monster only opens the fight.

Persistence. persist + saveStorage: state objects are kept as-is in memory and encoded to one line of text only when written (debounced 2 s, and synchronously on pagehide). On start the storage reads current (or backup, or the old IndexedDB vault once), decodes and validates it with sanitizeSave, merge rebuilds rates and sets isHydrated; onRehydrateStorage then enables writing. The initial in-memory world is a fixed placeholder (so the server render and the first client render match); a player without a save gets a random start in merge. The browser copy is a cache and the export path; the account holds the verified copy.

See also: computeOfflineGrant, SAVE_SCHEMA

State

The map (World)

Source: src/utils/world.ts:32

The map has no edge. GameState.tiles is a World: an immutable, sparse set of the explored tiles on an integer grid with negative coordinates, stored as ReadonlyMap<number, Tile> under a small-integer key (tileKey(x, y), |x|, |y| <= COORD_LIMIT = 16,000, at most MAX_OWNED_TILES = 250,000 tiles). Unexplored land is simply absent (getTile gives undefined, tileAt an empty tile). Updates are copy-on-write (setTile, patchTile, batched setTiles), so state.tiles changes exactly when the map does; the owned / building / chest / per-biome counters and the bounding box are kept up to date incrementally (O(1) reads, no per-tick scans).

Tiles an old save knew by row and column keep their logical coordinates: the castle stays at (25, 25), so old saves and the procedural art (which hashes absolute coordinates, parity-tested against Python) are unchanged.

  • Reads go through getTile / tileAt / isOwnedAt / hasOwnedNeighbour / forEachOwned / ownedRowMajor (a cached row-then-column order, so seeded pickers and saves do not depend on the order tiles were added). buyTile checks hasOwnedNeighbour, the coordinate range and the tile limit.
  • A purchase costs one Map copy (about 16 ms at 50,000 tiles, mostly that copy plus the income pass); npm run perf prints the timings at 5k / 50k / 250k tiles.
  • Tests that were written for the old 50 x 50 array use worldFromRows / rowsOf / gridCells / tileAt from tests/helpers.ts.
  • The map you can pan over is limited by clampPosition (src/lib/mapView.ts): the middle of the screen stays within the explored land's bounding box plus PAN_MARGIN_TILES (6). Nothing else limits panning, and zoom steps do not depend on the map size.

Rendering

Rendering the map

Source: src/components/game/Grid.tsx:1

Rendering notes.

  • Grid mounts only the tiles that matter on screen: explored tiles and the unexplored ones touching them (what can be bought), inside the visible range plus two tiles. The list is rebuilt when that integer range or the map changes, not on every pixel of panning. The pan / zoom position lives in viewStore; fling inertia keeps its velocity in a ref with friction (no per-frame React state). The world div is a zero-size origin placed with translate() scale(); everything inside is positioned in world pixels, negative ones included.
  • Wheel zoom is stepped (0.75 / 1 / 1.5 / 2, one step per 50 px of wheel delta) so the pixel art stays crisp and zooms around the cursor. The zoom is exposed to CSS as --map-zoom; tile tooltips scale with it, castle/building dialogs do not.
  • Terrain: the ground is drawn in chunks of 16 x 16 tiles (768 px, CHUNK_TILES), one <canvas> each (TerrainLayer / TerrainChunk), only for the chunks on screen plus a ring around them, by terrainRenderer.ts from the atlas in public/pixel/terrain/
    • src/config/terrainAtlas.json. A chunk's picture depends only on the ground inside the chunk plus CHUNK_HALO (5) tiles, so its chunkSignature (one character per tile of that window, building tiles upper case) decides when it is redrawn: a purchase redraws the chunks next to it, never pan, zoom or a chest toggle. Draws are queued and run within a 6 ms frame budget (at least one chunk per frame); flat colours show first and until the atlas loads. Tiles are transparent hit areas that carry the castle, buildings, chest, '?' marker and hover overlays. Buyable unexplored tiles are drawn as the dark 'mist' sea. tests/world/terrainChunks.test.ts checks the halo is enough, that equal signatures mean equal pictures, and that nothing is cut at a border.
  • Highlight: the tile menu's "Highlight this ... area" tints the connected same-biome area (connectedCluster, an iterative flood fill) with the biome's colour from biomePalette.ts for 3 s, drawn by HighlightLayer as one screen-space canvas.
  • Minimap: Minimap paints one square per explored tile in its biome colour into one ImageData (src/lib/minimap.ts, repainted at most every 200 ms), a gold marker on the castle, purple ones on workshops, and outlines the visible part. Click or drag centres the view there; it is outside the map's click area, so it never pays gold.
  • Buildings keep their tile's own ground and get a pad of that biome (allPads() in terrain.ts, art in terrain_pads.py); the same rule is ported to terrain_logic.py and covered by the parity fixture.
  • Tile tooltips are portalled into MapTipLayer, a layer above the critters, because every tile is its own stacking context. NotifyDot is the one "needs attention" marker (unspent stat points, an affordable farm animal or upgrade).
  • A Tile reads only primitives from the store and takes canAfford from Grid, which works the price of the next tile out once for all of them; unchanged tiles are skipped by React.memo, so panning mounts only the tiles that enter the view.
  • AmbientLife spawns a critter every few seconds on an owned tile in view; they are purely decorative (no clicks, no rewards) and off when disabled in Settings, when the tab is hidden, and with prefers-reduced-motion.
  • Tutorial, stat tooltips and cost lists are generated from config constants, so they cannot drift from the rules. Font: Mozilla Headline (self-hosted, --font-pixel).

What the pace rests on

  • Castle timers are the floor of the first run. Levels 2-6 take 30 min, 2 h, 6 h, 12 h and 24 h (1 d 20 h 30 min in all), levels 7-10 another 1.5, 2, 2.5 and 3.5 days (11 d 8 h 30 min to castle 10); Master Builders shortens them.   • Tile price in materials (TILE_RESOURCE_COST). The sim prints, per tile count, the minutes the income needs to cover what is missing of each part of the next tile (table at the end of sim-milestones.md). Gold must stay the biggest number; if hide or stone becomes the limiter, adjust the farm (deer and pigs make hide, Tannery +25 %, Pasture +8 %) rather than the share.
  • Tile XP is small on purpose (BASE_XP_PER_TILE 45) and the level curve is slow and lifetime, so levels come from passive XP, kills and rebirth-paced play, not from buying tiles.
  • Combat is in the sim: the human* profiles fight a normal monster every 900 s and the plains boss every 3 h with a gear schedule (starter kit, knight gear from day 1.5, obsidian from day 5; an assumption taken from docs/generated/fight-sim.md), paying the real kill income.

Caveats. The human is one calibration point, not a measurement of players; the bots still beat it by 2-3x. The pacing guard and CI sharding

Source: scripts/pacing-guard.ts:1

The pacing guard, and how CI generates the docs.

npm run sim writes docs/generated/sim-baseline.json; CI (job generated) runs this script, which compares it with the copy on the base branch and fails the PR when a guarded milestone moves by more than +-15 % or by more than 5 game days (PACING_MAX_DRIFT_DAYS in scripts/pacingCompare.ts; without it a milestone at day 220 could drift for a month inside 15 %). An intended pacing change carries the pacing-change label: the guard then prints the report and passes. The label only takes effect on a new run, so re-run the job after adding it.

CI sharding. The job generated is three stages: scope (does the PR touch what the docs come from), generate (a matrix that runs in parallel: the profile hardcore-rebirth6-x10 alone, about 5 minutes; every other sim profile via --except; the three groups docs:gen:rest:quick|fights|loot of the other generators; a new generator goes into one of those scripts), and generated (the required check), which downloads the shards, runs sim --merge and then the two gates (stale docs, pacing guard). The end-to-end test account

The one account every end-to-end test signs in with (docs/reference/ops.md). The password is never in the repo: the person running the test types it.

Every test that needs a real login uses one account: lepryko@gmail.com. No other account is used for browser tests, manual checks of the server, or experiments with saves. The account lives in the Supabase project that .env.local points at. Its password is never in the repo. Two ways to sign in: by hand (the default; the test opens Chrome and waits for the person to sign in) or from .env.local (E2E_TEST_PASSWORD=... in your git-ignored .env.local; npm run e2e then signs in through the app's own /api/auth/login route; E2E_MANUAL_LOGIN=1 forces the by-hand path; traces are off so the password is never recorded). Run this yourself in your own terminal; an assistant does not read .env.local or run the test with the password set.

  1. Clear the account so the run starts from a new game: npm run reset-test-account (dry run), then npm run reset-test-account -- --yes. It needs SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY; check which project they point at.
  2. Run the smoke test: npm run e2e. Without E2E_TEST_PASSWORD sign in when the browser window opens (the test waits up to ten minutes). It fails if the account is not the test account. It starts the dev server on port 3004 (or reuses one that runs), opens your installed Chrome (E2E_CHANNEL=chromium uses Playwright's own browser) and runs e2e/smoke.spec.ts. It is a local run, not part of CI, because CI has no login and no test project.

reset-test-account finds the account by e-mail and runs the season reset for that one user with --hard --reset-gems --purge-history --no-backup: it clears the save (map, buildings, castle, level, XP, rebirths, Embers, worlds and stats), the whole ledger (bag, gear, fight, spawn timers, tickets, rebirths), the rebirth history and the rollback copies, and puts the gems back to the starting amount. It keeps the login and the profile (character name and class). The e-mail is hard-coded here; the script has no option to point at another user.
