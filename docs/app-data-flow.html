1. System overview

The browser renders and simulates ordinary time locally. It does not connect to Supabase directly. Next.js route handlers read the HttpOnly session cookie, validate small requests, and use a server-only Supabase client plus the game services. This boundary prevents clients from deciding rewards, spawns, or fight outcomes.

Local responsibility

Fast UI, ordinary resource/time progression, map display, cached save, and visualizing a server-provided combat plan.

Server authority

Cloud-save acceptance, absence rewards, chest contents, monster tickets, combat, inventory mutations, crafting and gems.

Database responsibility

Durable account state. RLS limits player reads; service-role code performs game writes.

2. Startup, persistence, and cloud sync

A browser copy makes first paint and offline use responsive; the signed-in account’s verified cloud save is the shared source for server gameplay. The owner tab claims time away before it starts its local tick or background synchronization.

1
Hydrate a safe local game. gameStore.ts reads through saveStorage, validates with sanitizeSave.ts, and rebuilds derived rates. It resets local combat because combat belongs to the server.
2
Establish the single owner. GameApp.tsx waits for useSingleTab; only the owner ticks, claims absence, polls, and uploads.
3
Claim time away, then ask for current tickets. useOfflineClaim.ts uses a reusable claim ID. useSpawnSync.ts obtains chests, monsters, combat events, inventory versioning, and the next poll time.
4
Persist locally, then synchronize cloud state. Local writes are debounced and flushed on pagehide. useCloudSync.ts uploads milestones/idle checkpoints and resolves revision conflicts without silently overwriting a newer active session.

3. Authoritative gameplay loop

The important distinction: map clicks and ordinary economy actions can change the local store; rewards and contested state must be confirmed by the server. Server responses are reconciled back into the stores and rendered by React.

Guest mode is deliberately different. /guest uses a local copy of the server engine and never calls Supabase. Treat it as an isolated browser-only game; do not infer production-account behavior from it.

4. Domain ownership map

Start in the domain closest to the intended rule. Config is data, game math is pure where possible, stores compose client behavior, and route/service pairs enforce server authority.

UI and client orchestration

  • src/app/GameApp.tsx — lifecycle composition
  • src/components/game/ — map, windows, dialogs
  • src/hooks/ — browser lifecycle and sync
  • src/stores/ — game, UI, settings, feature slices

Rules and local simulation

  • src/config/ — tunable values
  • src/catalog/ — item and content data
  • src/utils/game/ — pure economy/map math
  • sanitizeSave.ts — persisted-shape validation

Server game engine

  • src/app/api/ — HTTP boundary
  • src/lib/offline/ — ledger, rewards, combat, tickets
  • src/lib/cloudSave/ — save acceptance/versioning
  • src/lib/supabase/ — server clients

5. Change safely

Changing a local rule

Locate the config and pure function, then the store action that validates/mutates it. Update its nearby JSDoc and focused tests in the same change.

Changing server-authoritative behavior

Trace route → parser → service → repository/ledger → client reconciler. Keep request bodies intent-only; do not let a client name a reward amount or elapsed duration.

Changing save shape

Maintain additive compatibility. Validate through sanitizeSave, preserve fixtures, and add an upgrade when a schema bump is genuinely necessary.
